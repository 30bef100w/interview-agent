# 四组检索开发评测

输入为最新9,000条记录对应的离线图（8,704道Question），不启用草稿。24个手工构造需求、2个固定随机种子，每组前10题。

| 组别 | 定义 |
|---|---|
| original_tags | 线上B路评分组件：原始标签、岗位及原文匹配；不是完整线上流水线 |
| flat_semantic | 复用AI标注的直接知识点/场景关系，去掉知识层级与场景知识扩展 |
| graph_rules | MG/KG有限随机BFS、结构分、内容去重、30题短名单及最终双路配额 |
| graph_llm | 完全相同的图候选和30题短名单，由独立5.6代理做真实语义排序，再用相同最终配额 |

## 顺序

1. `eval_graph_four_arm.py prepare --protocol backend/data/eval/graph_four_arm_v3/protocol.json --out <新目录>`：冻结三组本地结果、两份LLM重排输入，以及三份独立盲评输入。盲评池包含所有图短名单和原始/细标签前10题，在看到重排结果前确定。
2. 重排代理只读其`rerank_packet_N.json`。为每个case输出全部候选ID的排列到`rerank_results/*.json`。必须是真实模型逐题判断，禁止关键词/字符相似度替代。
3. 与重排器隔离的评审代理只读其`judge_packet_N.json`，每对需求和题目打0/1/2分并解释，保存`judge_results/*.json`。不读取方法、排序、图标签、来源和旧评分。
4. `eval_graph_four_arm.py finalize --out <目录>`：强制检验每个重排结果是精确排列，应用相同配额；不会重新生成评审输入。
5. `eval_graph_four_arm.py score --out <目录>`：拒绝漏评/重复/额外评分，以固定K计算P@10，按需求平均两次随机结果，再做需求级配对bootstrap。

模型调用由Codex子代理完成，脚本只负责数据、结构校验和统计，没有自动替代模型的后备评分器。新运行需要重新调用模型；已有输入、输出可直接复算统计，不能把缓存重放延迟当成新模型延迟。

盲评只有原始需求、题干、答案前800字和已有上下文正文引用。0=无关/无法判断，1=辅助相关，2=直接覆盖明确需求。没有标签作为答案，不调用旧评分文件。池化nDCG使用所有组共同的已评池作为理想排序；没有全库gold，不报告全库Recall。

本地延迟用perf_counter，5次热重复，包含候选处理/内容去重/名额选择，排除图加载与LLM。另保存重排代理自记批次墙钟，含读取、推理、工具与输出，不把批次摊销当作单次API延迟，未单独测首次计时前排队。协议中对“含排队”的概述以此实际计时边界为准。

这是受控开发实验，手工确定场景/知识种子，未测试简历解析；重排与盲评虽然实例隔离，仍来自同一模型家族。最新报告和审计包以docs中的四组评测文件为准。生产面试引擎未接入本次实验重排器。
