## 一、两张逻辑图，共享实体

- **MG：知识目录与源题库。** 知识点逐层组织，题目挂载到实际考察的知识点，原题、答案及来源保留。
- **KG：业务场景/应用任务索引。** 按业务对象和任务匹配，例如本地生活服务、外卖服务。黑马点评归本地生活，苍穹外卖归外卖；教程名保留为来源属性，不单设入口。入口连接有明确业务依据的题目和知识点。
- 两者共用同一个知识点 ID 和题目 ID。KG 的 Redis 就是 MG 的 Redis，不创建副本，也不增加连接两个 Redis 的桥接节点。
- 入口不强制拆为“业务→项目类型→项目模板→模块→主题”。按业务/应用定义复用平级入口，不要求简历写教程名称。业务归类不等于具体项目身份合并，项目名、来源及实现仍保留为属性。

```text
KG 入口：本地生活服务（黑马点评等为来源示例）
  ├─涉及→ Redis（MG/KG 共享节点）
  ├─涉及→ 高并发（共享节点）
  ├─涉及→ 秒杀（共享节点）
  └─直接相关题→ Q1

MG：Redis ─细分→ Redis 缓存 ─细分→ 缓存穿透
Q1 ─考察→ 缓存穿透
Q1 ─依赖→ Redis（仅在题目上下文确有依据时）
Q2 ─考察→ 秒杀、防超卖（可同时挂多个点）
```

这是结构示意，不是对当前题目内容的标注结论。“缓存”与“Redis 缓存”是否分设取决于语义范围；不能把所有缓存知识强行归为 Redis 专属。

## 二、固定节点和关系含义

核心语义节点只需三类：知识点 `Concept`、项目/场景 `Scene`、题目 `Question`。现有来源文档、原始出现记录继续作为溯源辅助数据，岗位和面试维度也可保留辅助索引，但不能混进技术知识层级。

| 关系 | 起点 → 终点 | 何时建立 |
| --- | --- | --- |
| 细分 `HAS_SUBTOPIC` | 知识点 → 知识点 | 下级是上级范围内的细分；允许多父，禁止环 |
| 涉及主题 `COVERS_TOPIC` | 知识点 → 知识点 | 技术/能力涉及该主题，但不适合断言为上下级；不能只因经常一起出现就建立 |
| 考察 `TESTS` | 题目 → 知识点 | 回答本题实际需要解释、判断或运用的考点 |
| 依赖 `REQUIRES` | 题目 → 知识点 | 本题上下文明确依赖的技术或前置知识，但未必直接考察其原理 |
| 涉及 `INVOLVES` | 场景 → 知识点 | 题干或明确项目上下文能证明该项目涉及该知识点 |
| 直接相关题 `HAS_QUESTION` | 场景 → 题目 | 题干直接点名，或所在明确项目章节能证明归属 |

`REQUIRES` 在2026-11-05的新建图器`build_annotation_graph_v2.py`中已支持；它不是必填项，不要求给全部旧题强行补齐。历史试跑脚本不作为当前入口。

不建立任意“相关”边，不把共同出现的知识点两两相连，不因共享知识点就连接两个项目。边有方向；主图定义不随可视化显示方向改变。

题目可以挂非叶子知识点，也可以挂多个知识点。若细知识点已经完整表达考点，不因其所有祖先存在就逐层补齐 `TESTS`。若题目确实分别考察上位机制和细节，则可同时保留。现有1267道同时挂祖先和后代的题需要按此判断，不能批量删除祖先标签。

## 三、知识点注册与新增规则

每个正式知识点至少记录：稳定 ID、中文名、定义/范围、同义名称、直接父节点、关系依据、审核状态。定义/范围可以先对歧义节点补充，不伪造为全量已具备。

标注时按以下顺序执行：

1. 先看本题对应的领域入口、现有层级和同层节点，判断题目真正考察什么。
2. 检查全局中文名和别名。不能只检查当前分支，因为同一个知识点可以跨多个领域复用。
3. 现有节点完全匹配则复用；只是不同叫法则登记别名；需要第二条合理父路径时复用节点并补关系，不另建副本。
4. 只有确实缺少独立语义时才提出新节点，同时给出中文名、范围、父节点及原题依据。模型完成语义核查后再纳入正式索引，不依赖脚本按英文前缀自动决定层级。
5. 每批输出新增与合并清单，核查后形成新的索引版本，再用于下一批标注。

待确认提案单独存放，不默认成为正式图节点。“新名字不在表里”不等于“新概念不存在”。历史 `draft` 节点需要按这些规则整理，不能机械全部通过或删除。

判断冗余看语义，不看题目数量：同义重复应合并，范围不同应保留；只挂一两题、暂时没有直接题目的导航节点，都不因此删除。ID 不因中文名或目录位置改变而变化，历史 ID 通过合并映射追溯。

## 四、逐题标注输出

| 字段 | 含义与要求 |
| --- | --- |
| `question_id` / `source_locator` | 当前题目身份和可定位原文；试跑的 S 编号需连同数据快照使用，不作为跨批次全局身份 |
| `tests` | 实际考察的现有知识点 ID；每项保留简短依据 |
| `requires` | 有依据的前置依赖；允许空 |
| `scenes` | 有依据的项目/场景 ID；说明依据是题干还是明确章节；允许空 |
| `scene_concept_links` | 本题能证明的“场景涉及知识点”关系；逐项判断，不能对所有场景和考点做笛卡尔积 |
| `proposed_concepts` / `proposed_scenes` | 缺失项提案，需范围、父节点（知识点）与依据；不得直接冒充已有正式节点 |
| `companies` / `roles` | 原有企业、岗位信息及核查状态；企业是属性，不创建企业节点，不从技术栈猜企业 |
| `review_status` | 区分初标、语义复核、待上下文；脚本结构校验不等于语义复核 |
| `reason` | 简短说明关键挂载判断，尤其是新增、合并、跨父挂载和场景归属 |

先读题干和必要上下文，再输出一批结构化标注。脚本负责格式、ID、引用、重复和环校验，不能用关键词规则替代逐题语义判断。原答案可提供线索，但答案中的所有术语不自动成为考点，原答案也不默认正确。

重要例子：题目同时提及“黑马点评”和“RPC项目”，又考察 Redis 和负载均衡，不能自动生成两个项目各自涉及这两个知识点的四条关系；要分别确认归属，不明确的关系待核查。

通用“如何防止超卖”题不能仅因涉及秒杀就挂到本地生活业务。“你的项目怎么做的？”缺少项目上下文时保留原文并标待补上下文，不补造项目和考点。

## 五、图的构建与属性

1. 读取指定版本的正式索引、合并映射和已判断标注，生成共享节点及明确关系；相同起点、关系、终点只保留一条边，多份依据聚合保存。
2. 旧技术/业务标签作为待核查线索保留，不能直接升级为语义审核通过的边。当前场景与考点的自动共现关系只能作为候选依据，不能直接当作已确认项目事实。
3. 企业作为题目属性；若多来源不同，保留各来源的企业记录及汇总值，不编造单一归属。年份、岗位、原标签等也保留为属性或辅助索引，不能混作技术节点。
4. 同题不同来源可指向同一题目，原文与答案分别留在来源记录中。时间戳和相同短题文本都不能单独作为合并依据；依赖不同上下文的短题不得误合并。当前3750个 Question 与3750个来源记录不代表已经完成跨来源语义去重。
5. 审核状态必须由明确的审核记录生成。不要因 `Graph.edge()` 默认 `draft` 而覆盖已审核结论，也不要把结构检查通过等同于语义通过。
6. 待补上下文题仍保留来源证据；对场景、知识点等所有挂载均标明未就绪状态，不能只清空技术标签就认定整题已处理。

## 七、离线图验收顺序

1. 以本规范固定节点和关系含义，修正建图脚本与旧说明的不一致。
2. 核查知识点的同义项、范围和父子关系，补充歧义定义；逐项记录合并与保留原因，不按低题量裁剪。
3. 按注册表复核已有题目标注，优先复核新增节点、上下文不足和多场景关联的题目，准确记录复核覆盖数。
4. 整理项目入口，分别核查“场景→题目”和“场景→知识点”，补齐对应来源依据。
5. 重建离线图，检查唯一性、关系端点、层级无环、别名合并、来源完整性和审核状态一致性；输出中文知识目录与真实项目子图供查看。

先完成并展示离线图，再另行讨论检索。当前没有把上述未完成项宣告为完成。

## 2026-11-04 场景粒度补充

同一项目不按交易、日志、风控、界面、技术栈或版本阶段拆成场景。简历模块决定考察重点，不限制其他合理追问；未写功能不代表未实现。通用补充题不能冒充项目原题，场景关系仍需逐项证据。
