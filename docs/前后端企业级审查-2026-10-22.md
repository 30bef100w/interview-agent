## 1. 结论与边界

项目已经有可运行的软件闭环、服务端资源归属检查、密码哈希、用户 Key 加密、生产配置检查、代码执行隔离和持续集成。Next.js + FastAPI + SQLAlchemy 的组合适合继续建设为模块化单体。

但当前尚不适合作为已经达到企业级生产标准的系统来描述。主要差距是：认证入口规则不一致、权限与会话撤销机制不完整、长连接与数据库事务生命周期不匹配、业务请求缺少幂等及并发保护、前端状态恢复不完整，以及发布/恢复缺少可验证的保障。

本次检查仅覆盖应用软件层：账户权限、HTTP/SSE/WebSocket、前端状态、简历文件、数据库、部署、日志及测试。没有评审 Agent 的规划、召回、追问或评分算法；没有更改业务代码，没有推送或部署，也没有向线上发送伪造回调、进行渗透或压力测试。

这是一轮源码审查与有针对性的本地诊断，不是完整安全认证或生产容量认证。未核验服务器真实配置、网关外层 TLS/WAF、云服务备份、真实流量指标或所有浏览器的视觉与无障碍体验。仓库缺少某项运维配置，不等于服务器上一定没有。

### 证据与优先级

- A：本轮本地隔离诊断已验证；使用临时/内存数据库、模拟外部请求，不调用付费模型。
- B：调用链或源码明确可达的缺陷/风险；没有做线上复现或容量压测。
- C：仓库层面的工程能力缺口，需结合生产环境和业务规模验收。
- P0：满足注明的暴露条件时，应阻断对外发布的权限/认证问题。
- P1：下一轮优先修复的正确性、数据保护或可用性问题。
- P2：应排期完善的性能、维护性、体验或防御纵深。

不同条目可能具有共同根因，不应按条目数推算重构工作量。

## 3. 应优先处理的认证与权限问题

### F01 — P0/A：飞书 Webhook 对缺失凭证采取放行策略

位置：`backend/app/services/feishu_events.py:64`、`:90`、`:98`；`backend/app/api/feishu.py:18`。

签名仅在请求同时携带 signature 且配置存在 sign_key 时检查。token 也只在请求提供非空 token 时比较。结果是“提供错误值会拒绝、不提供反而跳过”。即便服务器配置了验证信息，未签名且不带 token 的明文消息仍可进入分发。

本轮使用独立 FastAPI 测试应用，将分发函数替换为 mock：上述请求返回 HTTP 200，mock 被调用。没有向飞书或生产接口发送消息。

暴露条件与影响：该路由对外可达时，存在伪造入站消息的入口；后续影响受绑定用户、消息内容和运行配置影响。本次没有证明线上账号已经被冒用。

修复：根据飞书实际回调模式强制要求相应认证字段，缺失即拒绝；未配置安全认证时关闭事件入口；使用恒定时间比较；校验时间窗口；事件去重持久化并覆盖多进程/重启。目前进程内 512 条去重缓存不构成持久抗重放机制。

验收：缺失/错误认证、过期签名、重放消息均被拒绝或只处理一次；合法回调与 URL 验证仍通过；未配置时不接受业务事件。

### F02 — P0/A：用户名被用作自动管理员授权依据

位置：`backend/app/api/auth.py:31`；`backend/app/services/billing.py:20`；`backend/app/api/deps.py:31`。

公开注册会调用 `sync_admin_flag`，该函数按 `ADMIN_USERNAMES` 直接升权。如果配置名尚未注册，先注册该名的人即可成为管理员。另一问题是：管理员界面取消其管理员身份后，只要名字仍在配置中，下次鉴权就会重新升权。

修复：使用受控初始化命令创建首位管理员；运行期角色变更以数据库用户 ID 和审计记录为准。公开注册不执行提权。明确紧急恢复渠道，避免把普通请求变成隐式授权操作。

验收：配置保留名不能通过公开注册获得管理员；降权后所有通道均失去管理权限；角色变更记录与数据库写入具有一致性。

### F03 — P1/A：密码重置无法撤销旧会话，退出仅清本地 Token

位置：`backend/app/services/auth_service.py:17`；`backend/app/api/admin.py:353`；`frontend/lib/api.ts:23`。

JWT 只有用户标识和有效期，密码重置只改哈希，没有会话版本或撤销记录。旧凭证在默认有效期内仍可继续认证。当前退出登录主要是浏览器删除 Token，不能撤销已经复制出去的凭证。

修复：引入认证版本或服务端会话记录；密码重置/安全事件提升版本，撤销旧 HTTP 与 WS 会话。按业务需要使用短期访问凭证和可轮换刷新会话。保留“保持登录”的体验不需要在网页存储明文密码。

验收：改密、强制下线后旧凭证不能继续访问；多设备会话策略明确；保留正常刷新登录能力。

### F04 — P1/A：WebSocket 与 HTTP 的账号权限及输入规则不同

位置：`backend/app/api/interview_ws.py:100`、`:165`；对照 `backend/app/api/deps.py` 与 `backend/app/schemas/api.py`。

WebSocket 握手检查 JWT 和会话归属，却没有读取用户的禁用状态。后续答题线程虽读取用户，也没有执行与 HTTP 相同的禁用检查。HTTP 限制答案最长 2000 字，而 WS 把 text 转成字符串后仅检查是否为空。非对象 JSON 消息也没有统一 schema 校验。

本轮本地 WebSocket 测试中，被禁用用户仍收到 snapshot，2001 字答案到达模拟处理器。

修复：所有入口复用同一认证、资源授权和消息 schema；连接建立时及敏感消息处理时检查账号有效性。认证过期/封禁后应终止或拒绝后续操作。Origin 校验作为额外策略，但不能把“允许跨域连接”本身等同于无凭证越权。

验收：HTTP/WS 对禁用、过期、越权、长度错误、错误 JSON 类型给出一致结果；封禁后已有连接不能继续处理答案。

### F05 — P1/C：登录凭证传输与密钥生命周期需要加固

位置：`frontend/lib/api.ts`、`frontend/lib/ws.ts`、`deploy/nginx.conf`、`backend/app/services/llm/manager.py:91`。

登录 Token 存在 localStorage，WS 又把长期 Token 放在 URL 查询参数中，增加日志和脚本读取凭证的暴露面。仓库 Nginx 只配置 HTTP，未包含强制 HTTPS、HSTS 等策略；本轮未验证可能存在的外层 TLS 网关，不能断言生产没有 HTTPS。用户 Key 加密密钥由 JWT secret 派生，两类密钥轮换耦合。

修复：验证从公网入口开始强制 HTTPS/WSS；避免在 URL 中传长期 Token，可使用短期一次性 WS 票据；过滤认证日志。视部署拓扑设计 HttpOnly/Secure/SameSite 会话，并同步处理 CSRF；单独版本化用户 Key 的加密密钥。

验收：明确 TLS 终止边界；代理日志不含长期凭证；访问凭证和加密密钥可分别轮换。没有在本轮证明存在可利用的 XSS，localStorage 是防御纵深风险而非 XSS 证据。

## 4. 后端业务正确性与资源生命周期

### F06 — P1/A：空闲 WebSocket 长期占用数据库连接

位置：`backend/app/api/interview_ws.py:113`；`backend/app/db.py`。

握手创建 ORM Session 并执行查询后，没有在等待消息前结束事务/释放连接，直到断开才关闭 Session。默认 PostgreSQL 池为 5 个常驻连接加 10 个溢出连接，每个后端进程总计 15 个。若所有连接被这类空闲 WS 占据，HTTP 和答题子线程会竞争不到数据库连接。

本轮将本地 QueuePool 设为 1，保持一个空闲 WS 后池占用为 1，第二次数据库 checkout 超时。这验证连接生命周期问题，不等于已经完成真实 PostgreSQL 的并发容量测试。

修复：以每条消息/短事务为范围创建数据库 Session；把需要的标量读出后立即释放连接；异步入口避免直接执行长时间同步数据库 I/O。不要通过单纯调大连接池掩盖生命周期问题。

验收：大量空闲连接不长期占用同等数量数据库连接；连接数超过池容量时，普通 API 仍能在目标延迟内响应；断连和异常路径释放资源。

### F07 — P1/A+B：额度没有作为单场权益原子结算

位置：`backend/app/api/interview.py:57`、`:600`、`:682`；`backend/app/services/billing.py:43`。

创建成功后扣除一次额度，但后续答题仍要求剩余额度大于 0，因此最后一次面试开场后无法继续。检查与扣除分离，又缺少原子预占，多个并发创建可能在同一份余额下通过门禁。

修复：会话记录本场已授权的付费来源和权益；创建时在短事务中原子预占，成功确认、失败退回；本场继续答题不重复检查“还能否开新场”。调整额度也需要并发保护和一致审计。

验收：余额 1 时完整完成一场；同时创建多个任务最多占用可用次数；失败只退款一次；审计与余额一致。

### F08 — P1/B：答题缺少跨入口幂等和版本检查

位置：`backend/app/api/interview.py:848`；`backend/app/api/code.py:82`；`backend/app/models/interview.py`。

HTTP、SSE、WS、代码提交均可修改会话，没有共同的消息唯一 ID、期望题目/轮次版本和乐观并发控制。重试、双标签页、渠道同时操作可能重复处理，或者后写覆盖先写的 state_json。Question 也没有 `(session_id, q_index)` 的唯一约束兜底。

修复：统一提交命令，携带 submission_id、question/turn_id、expected_version；持久化去重结果并使用短事务原子认领处理权。耗时外部调用期间不要一直持有数据库行锁，完成时校验版本再提交。

验收：相同 submission_id 重试只处理一次；过期版本返回冲突及最新快照；并发答题/退出不能复活已结束会话或丢失已确认回答。

### F09 — P1/B：长任务没有持久化恢复协议

位置：`backend/app/api/interview.py:600`、`:745`；`backend/app/services/feishu_dispatch.py`；`frontend/app/interview/new/page.tsx:162`。

创建依赖进程内 BackgroundTasks，答题/事件处理依赖 daemon thread；进程中断时任务本身不持久。当前持久化会话记录不足以直接重放完整创建请求，缺少统一的任务认领、重试和超时恢复。前端轮询没有取消机制，页面卸载后旧轮询仍可能继续，完成时触发过期跳转。

修复：先定义持久化任务及状态、参数、deadline、幂等键、失败原因、租约/心跳和恢复扫描，再按规模选择数据库任务表或队列。前端任务 ID 可恢复，轮询可取消并使用退避，完成后仅由当前有效页面导航。

验收：创建中重启、提交后断连、任务超时、重复投递都有明确终态和恢复入口；后台失败不永久停在 creating。

### F10 — P1/B：过载告警可能阻塞事件循环并放大故障

位置：`backend/app/middleware/load_alert_middleware.py:43`；`backend/app/services/feishu_notify.py:76`。

async 中间件直接调用同步 urllib 网络告警，超时设置 8 秒。超过流量阈值且告警服务不可用时，网络等待会阻塞事件循环；冷却时间仅在发送成功时更新，失败后后续请求还可能连续尝试。请求时间戳还按每次请求遍历列表，且为进程内状态。

修复：请求路径只记录轻量指标，异步有界队列发送告警；失败也应退避/熔断。计数使用有界窗口或共享指标体系。告警不得成为核心请求的同步依赖。

验收：把通知服务模拟为超时，健康接口和普通请求仍满足延迟目标；告警失败不形成持续重试风暴。

### F11 — P1/A：密码 schema 与哈希实现边界不一致

位置：`backend/app/schemas/auth.py`；`backend/app/api/admin.py:38`；`backend/app/services/auth_service.py:9`。

schema 限制的是字符数，bcrypt 限制的是 UTF-8 字节数。73 个英文字符、25 个汉字均能通过注册输入校验，但哈希时报错；管理员重置密码有同样问题，登录的密码字段也缺少相同边界。

修复：优先采用支持目标密码策略的哈希方案并保留旧哈希验证/渐进迁移；若继续 bcrypt，明确按字节校验并返回可读的 4xx。不要静默截断密码。

验收：中文、emoji、长密码、错误密码和旧账号登录均有确定行为，不出现未处理 500。

### F12 — P1/A+B：用户 Key 失效时错误地转用平台客户端

位置：`backend/app/services/llm/manager.py:105`；`backend/app/services/llm/client.py:65`；`backend/app/api/resume.py:136`、`:239`。

用户 Key 解密失败返回空字符串，客户端构造逻辑随后退回默认平台客户端。本轮 mock 默认客户端验证了这条路径。额度判断却按“数据库里有自填 Key”分类，可能与实际付费来源不一致。

此外，简历画像/分析直接创建默认客户端，未统一走用户配置及用量记录入口。本条评审的是应用配置和计费一致性，不涉及模型或 Agent 策略。

修复：凭证损坏/失效时 fail closed，明确提示重新配置；使用统一的模型服务配置和用量记录入口，实际计费来源在调用前确定并审计。

验收：密文损坏或轮换后不能静默消耗平台 Key；各 AI 功能的配置、实际请求来源和用量归属一致。

### F13 — P1/B：昂贵操作缺少应用级配额与限流

位置：`backend/app/api/auth.py`、`backend/app/api/resume.py`、`backend/app/api/code.py`；`backend/app/middleware/load_alert_middleware.py`。

流量中间件只有告警，没有实际限流。公开注册附赠额度，缺少可见的注册/登录滥用控制。简历解析、分析可以反复触发，只检查用户是否还有面试次数，并不按调用消耗相应预算。判题虽有每进程 2 个槽位，但没有跨进程/多实例的统一容量策略。

修复：按用户/IP/动作配置速率和并发限制，登录失败退避，昂贵操作设置独立预算、缓存和排队上限。外层 WAF 可以补充，但不能替代应用内的用户权益控制。

验收：超限返回可预期的 429/繁忙提示及重试信息；重复分析不会无界产生费用；多进程容量配置一致。

### F14 — P1/B：文件解析与文件/数据库写入缺少完整边界

位置：`backend/app/api/resume.py:91`、`:170`；`backend/app/services/resume_service.py:8`。

PDF 全量读取到内存，应用本身未设置清晰的文件字节、页数、提取文本和解析耗时上限。Nginx 的 25MB 限制是已有缓解措施，但不能覆盖不同部署入口和解析后的资源开销。上传先写文件后提交数据库，提交失败可能留下孤儿文件；删除先删文件后提交，提交失败可能保留缺失文件的数据库记录。

修复：有界读取与类型/页数校验，解析超时及并发限制；文件采用暂存/确认或补偿清理流程，删除任务在数据库确认后执行并可重试。画像输入从任意 dict 改为有边界的结构化 schema，防止错误结构在后续普通接口触发异常。

验收：大文件、多页/坏 PDF、解析超时、数据库失败均能受控返回并清理资源；文件与记录可对账修复。

## 5. 前端状态与接口衔接

### F15 — P1/B：请求失败被误认为登录失效

位置：`frontend/components/AppShell.tsx:104`；`frontend/app/admin/layout.tsx`；`frontend/app/resume/upload/page.tsx:65`。

`/auth/me` 的 catch 无差别清 Token；简历列表失败也直接跳登录。网络错误、服务器 500、临时不可用会触发误退出。各页面又重复加载和处理用户信息，行为不统一。

修复：集中 AuthProvider/认证状态管理；明确区分 401、403、网络与 5xx，只有确实过期才撤销本地登录；提供可重试错误态。正确处理账号切换和过期请求，避免旧用户响应覆盖新状态。

验收：断网/500 保留有效凭证；明确 401 才进入重新认证；多标签页退出和账号切换一致。

### F16 — P1/B：简历异步返回能串写当前选中项

位置：`frontend/app/resume/upload/page.tsx:95`、`:170`、`:249`。

对 A 开始解析/分析后仍允许切换 B。A 返回时使用 `setSelected(prev => ({...prev, ...A结果}))`，没有比较 ID，页面会把 A 的结果展示为 B。用户再保存可能将 A 的画像持久化到 B。保存/删除等其他异步操作也需要相同审计。

修复：请求捕获实体 ID，结果按 ID 写入实体缓存；只有当前选中 ID 相符才更新编辑区。采用请求序号/取消，防止旧结果覆盖新编辑；删除与分析之间定义明确的互斥或冲突策略。

验收：A/B 快速切换、反向返回、处理中删除、重复上传不串写；未保存编辑有离开提醒。

### F17 — P1/B：答案和代码草稿容易丢失

位置：`frontend/app/interview/[sessionId]/page.tsx:351`；`frontend/components/CodeEditor.tsx:271`。

发送前清空答案输入，失败不恢复原文；代码仅存组件 state/ref，刷新、离开或重新挂载可丢失。乐观显示的答案也没有明确的发送中/失败状态，刷新快照后可能消失。

修复：草稿以 user/session/question/language/mode 隔离保存；提交后等服务端确认再清除；保留失败重试入口；持久化数据应有删除和过期策略，不将敏感内容无限留在共享浏览器。

验收：离线发送、刷新、语言切换、模板更新、页面恢复都不丢草稿；已确认消息重试不重复提交。

### F18 — P1/A：WS/SSE 缺少完整的异常结束与恢复协议

位置：`frontend/hooks/useInterviewWebSocket.ts:112`；`frontend/lib/sse.ts:32`；`frontend/app/interview/[sessionId]/page.tsx`。

WS 发送中关闭连接时不会安排重连；SSE 收到部分 token 后无 done/error 就结束，函数静默返回，页面可能一直等待。已有快照恢复能力，但不能替代提交确认和终态处理。

本轮使用模拟 WebSocket/ReadableStream 验证：发送中断线安排的重连定时器为 0；SSE 的 token 回调为 1、done/error 均为 0。

修复：请求有唯一 ID 与明确状态；EOF 未收到终态视为未完成，查询服务端再恢复；分开管理连接状态和提交状态；设置整体/空闲超时、取消和清理。JSON 解析或事件回调异常也不能被无声吞掉。

验收：发送前/中/后断网、半包、无终态、刷新、认证过期都可恢复，且不重复推进会话。

### F19 — P2/A+B：错误结构、接口类型和取消机制缺少统一约定

位置：`frontend/lib/api.ts:35`、`frontend/lib/sse.ts`；`backend/app/schemas/api.py`。

FastAPI 校验错误的 detail 为数组时被转换成 `[object Object]`，已本地复现。前端各页面手写返回类型，多个请求通道重复拼认证与错误解析；缺少统一超时和调用方取消，列表请求也没有防止过期响应覆盖当前筛选条件。

修复：统一可读错误转换和错误码/字段错误/trace_id；通过 OpenAPI 生成接口类型；普通 HTTP、SSE、WS 共享认证与消息 schema。AbortSignal 可贯穿请求，但非幂等提交不能取消后盲目自动重试。

验收：422/401/403/409/429/503 和网络错误均有可执行提示；旧筛选结果不能覆盖新结果；后端契约变化能在 CI 被发现。

### F20 — P2/B：浏览器本地数据没有按用户隔离

位置：`frontend/lib/notifications.ts:16`；`frontend/app/resume/upload/page.tsx`；`frontend/components/OnboardingModal.tsx`；AppShell logout。

通知、默认简历、新手引导使用全局存储 Key；退出只清理少量登录字段。共用浏览器切换账号后，通知内容和偏好可能残留或串用。这是浏览器内隔离问题，不代表后端跨账号数据权限已经失效。

修复：按稳定用户 ID 命名空间存储；账号切换清理内存缓存；敏感通知考虑服务端存储；退出/注销策略明确。

验收：同浏览器 A 退出后 B 看不到 A 的本地通知和草稿；新账号不会继承旧账号的新手状态；跨设备行为符合产品约定。

### F21 — P2/B+C：手机端入口和外部资源可用性不完整

位置：`frontend/components/AppShell.tsx:249`；`frontend/components/CodeEditor.tsx:8`；`frontend/app/layout.tsx:28`。

手机导航只显示前五项，缺少覆盖其余模块的统一“更多”入口；代码区固定双列，需要小屏单栏/标签切换。Monaco 从第三方镜像加载，字体依赖 Google，核心编辑体验及构建依赖外网。受限网络构建已出现字体下载失败。

修复：完善手机信息架构、软键盘/安全区和编辑器降级；核心静态资源随版本部署，字体本地化或提供可靠回退；弹窗补焦点管理、键盘和读屏验收。本轮没有进行所有尺寸/辅助技术的人工视觉测试。

验收：常见窄屏可到达全部主要功能；外部 CDN 不可用仍可编辑与提交代码；生产构建不需要不受控字体下载。

## 6. 数据、部署与可运维性

### F22 — P2/B：列表分页在内存执行，管理列表存在 N+1 查询

位置：`backend/app/api/interview.py:1005`；`backend/app/api/admin.py:46`；`backend/app/services/llm_usage_stats.py`。

历史接口先读取用户全部会话及大 JSON 字段，再过滤切片。管理员列表逐用户查询场次数、配置、费用等，查询数随页大小增长；用量查询也先加载全部调用记录再聚合。

修复：SQL 完成筛选/聚合/COUNT/分页，只查询列表需要的列；基于实际查询计划补组合索引。稳定分页增加确定性次排序，必要时再使用游标分页。

验收：用足量合成数据测查询计划、查询数和 P95 延迟；单页大小固定时查询数量不线性增长；不能以小数据集响应快替代性能验收。

### F23 — P1/A+B：数据库迁移、约束与数据真源缺少统一治理

位置：`backend/app/db_migrate.py`；`backend/app/db.py`；`backend/app/models/interview.py`。

启动时 create_all + 补列没有版本化迁移和回滚记录；多实例启动可能竞争 DDL。SQLite 实际应用引擎未开启外键执行，声明 ForeignKey 并不意味着 SQLite 已执行约束。部分业务唯一性缺少数据库约束。会话状态又同时存在独立列、state_json、plan_json、问答表和 checkpoint，缺少明确的真源、版本与修复约定。

修复：使用受控 Alembic 迁移作发布前步骤；给关键唯一性/非负余额等补约束；SQLite 启用外键并验证现有数据，生产以 PostgreSQL 为主要验收对象。为状态副本明确权威来源、版本及重建方式，避免把所有 JSON 一次性重构成复杂事件系统。

验收：空库安装、旧库升级、重复启动、失败恢复和历史数据校验一致；数据库拒绝孤儿关系及重复业务键；副本可从真源恢复。

### F24 — P2/A：日期存储和接口输出存在时区歧义

位置：`backend/app/models/user.py`、`backend/app/models/interview.py`；`backend/app/api/interview.py:1045`。

默认值生成 UTC aware datetime，但列为不带 timezone 的 DateTime，读取后可能成为 naive datetime；部分接口直接 isoformat 输出。浏览器把不带偏移的日期当本地时间解析，可能导致显示和时间筛选偏移。SQLite 往返后的 tzinfo=None 已验证。

修复：统一数据库与接口时区策略，输出明确的 UTC Z 或偏移；PostgreSQL 可使用时区列；迁移已有 naive 时间时明确其原始语义，不能盲目加偏移。

验收：至少在 UTC、Asia/Shanghai 客户端验证同一事件一致；日报和日期边界口径清楚。

### F25 — P1/C：发布健康检查与恢复能力不能证明业务可用

位置：`backend/app/main.py`、`docker-compose.yml`、`deploy/update.sh`、`deploy/health_watchdog.py`。

health 仅返回固定正常信息，不验证数据库/迁移就绪或关键存储。更新脚本直接 pull + 重建并请求健康接口，缺少明确等待、业务冒烟、版本回滚和迁移兼容检查。仓库没有可验收的 PostgreSQL/上传文件备份及恢复演练流程；服务器外部可能另有建设，本轮未核查。

修复：区分 liveness/readiness/dependency status；发布前检查配置和迁移，发布后轮询就绪及业务冒烟，记录可回滚镜像。确定数据库与文件的 RPO/RTO，安排异机备份和真实恢复演练。Redis 当前禁用持久化可作为可重建缓存，但不能因此宣称全部业务数据没有持久化。

验收：数据库断开时 readiness 非正常；发布失败有明确退出与回退步骤；从备份恢复数据库和简历文件后，账号及历史记录可用。

### F26 — P2/C：构建可复现性和容器最小权限需要补齐

位置：`backend/requirements.txt`、前后端 Dockerfile、`.github/workflows/ci.yml`。

Python 依赖多数未锁定，基础镜像不是不可变摘要；测试和部署可能获取不同版本。Web 容器未显式设置非 root 用户；后端仍安装编译工具链，前端运行镜像复制完整 node_modules，存在瘦身空间。此处是 API/前端镜像加固，不是重复宣称已修复的判题容器没有非 root。

修复：管理依赖锁文件及受控升级，生成 SBOM 并扫描实际锁定版本；普通应用非 root、最小镜像与必要的文件写权限；设置资源边界。核心静态资源本地化，固定生产 Node/Python 版本并在相同版本测试。

验收：同版本可复现构建；镜像有扫描结果及处理策略；正常运行不依赖 root。没有执行漏洞数据库扫描，因此本报告不声称发现具体依赖 CVE。

### F27 — P2/B+C：日志留存、隐私删除与审计一致性不完整

位置：`backend/app/main.py:38`；`backend/app/services/system_log.py`；`backend/app/services/session_checkpoint.py`；`backend/app/api/resume.py:170`；管理员 `_audit`。

日志使用普通 FileHandler，文件 trace/checkpoint 的落盘兜底没有统一留存清理；异常详情没有集中脱敏边界。简历关联会话后拒绝删除，尚无完整的用户数据删除/匿名化流程。部分管理审计在业务提交后另写且失败被吞掉，不能作为强一致合规审计使用。

修复：日志结构化、脱敏、轮转/集中采集、配额与留存策略；区分运营日志和安全审计，重要审计与业务原子写入或 outbox 投递。提供文件、文本、副本、通知及备份保留口径一致的数据删除/匿名化方案。

验收：日志中无长期凭证/Key，磁盘增长受控；按用户查清数据足迹并执行删除策略；关键权限变更必有可追溯记录。本轮没有读取真实用户简历或验证历史日志是否已经泄漏敏感数据。

## 7. 测试与架构建设

### F28 — P1/C：测试通过与企业级验收之间存在明显缺口

位置：`frontend/tests/auth-storage.test.mjs`；`backend/tests/`；`.github/workflows/ci.yml`。

当前测试能验证已有逻辑，但上述本地复现问题仍能在全绿基线中存在。前端只有登录缓存相关测试，缺少组件与 E2E 交互。未见完整的多用户权限矩阵、真实 PostgreSQL 事务与迁移集成测试、断网/并发/故障注入、发布恢复验收。现有代码隔离 CI 应保留，不能因其他缺口否定它。

建议的最低验收集：

1. 用户 A 无法读写 B 的简历、原文件、会话、报告和复盘笔记。
2. 注册保留名、角色降权、账号禁用、改密与强制下线覆盖 HTTP/WS/后台入口。
3. 回调缺失/错误签名和重复事件测试。
4. 余额 1 完成整场、并发创建、失败退款与重复退款测试。
5. 重复答案、双标签页、答案与退出并发，不重复处理、不覆盖新状态。
6. 发送中断网、SSE 缺最终事件、刷新、重新连接与草稿恢复测试。
7. 简历 A/B 切换与反向响应，处理中删除和上传失败测试。
8. 空库安装、旧库升级、真实 PostgreSQL 约束/事务和连接池测试。
9. 通知服务超时、数据库中断、进程重启、外部字体/CDN 不可用的降级测试。
10. 数据备份恢复与发布回滚演练，验证业务记录而非只检查 HTTP 200。

负载测试应使用隔离环境的合成用户和数据，先确定连接数、延迟、错误率及资源目标，不能直接压生产平台。

### F29 — P2/B：业务边界需要收敛为共享服务，而非重复入口逻辑

位置：`backend/app/api/code.py`、`backend/app/api/interview_ws.py` 直接导入 interview API 的私有函数；前端多页面同时承担请求、认证和业务状态。

建议结构：

```text
前端页面/组件 → 业务 Hook 与实体缓存 → 统一 API/流式通信层
                           ↘ 认证上下文、草稿与错误状态

HTTP / SSE / WS / 外部回调 → 应用业务服务 → 数据访问与短事务
                                      ↘ 文件/后台任务/通知等适配器
```

共享服务应统一鉴权、幂等、额度与事务边界。业务服务不应依赖某个 HTTP router 的私有函数。优先抽取认证、简历、会话业务，随修复逐步迁移；无需为了“企业级”立即引入微服务、Kubernetes、完整 DDD、Kafka 或分布式事务。

验收：同一业务在所有通道下语义一致；业务层可用 fake adapter 独立测试；新增入口不复制权限/扣费逻辑。

## 9. 最终判断

可以继续在现有技术栈上迭代。当前最需要投入的是认证一致性、数据正确性、连接与任务生命周期、失败恢复和可验证测试，而不是增加更多基础设施名称。

报告中标为 A 的行为已在本地验证；B/C 条目需要按验收标准补测试或生产配置核查。修复后应重新执行回归与企业级验收，不能将“发现并写入报告”视为“已修好”。

本轮仅新增本审查文档；没有修改业务代码、默认构建配置，没有提交、推送或部署。
