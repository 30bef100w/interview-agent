# AI 面试模拟器 — 迭代与踩坑历史（答辩手册）

> 目的：面试官问「这个项目你踩过什么坑 / 怎么迭代的」时，能按 **现象 → 根因 → 修复 → 原则** 讲清楚。  
> 时间线大致覆盖 2026-08 前后的密集迭代（与仓库当前实现对齐）。  
> 配合阅读：`docs/设计文档-后端与Agent.md`。

## 0. 怎么用这份文档应付面试

推荐叙事结构（每个坑 45–90 秒）：

1. **场景**：用户 / 我自己测到了什么  
2. **错误归因排雷**：一开始以为是 X，实际是 Y  
3. **根因**：一句话技术 why  
4. **修复**：控制面改在哪一层（引擎 / 检索 / Prompt / 前端）  
5. **沉淀原则**：可迁移到别的 AI 应用  

文末有「高频追问速答」。

## 2. 踩坑详单

### 坑 1：算法题聊到了，编辑器却不出现

| | |
|--|--|
| **现象** | 对话里已经进入算法题，底部仍是普通输入框，Monaco 不出来 |
| **误判** | 「后端没下发 coding」或「题型判断错了」 |
| **根因** | 答题接口返回后，前端只更新了 `message/stage`，**没有重新 GET session**；`current_coding` 仍为空，渲染条件不满足 |
| **修复** | 答题成功后强制拉齐服务端会话快照，用 `history + current_coding` 驱动 UI |
| **原则** | 有状态的 AI 产品：**服务端状态是真相**；客户端不能只信增量字段 |

**面试怎么说**  
> 这是前后端状态同步问题。算法题是否展示取决于 session 里的当前题类型，我后来改成每次答题后以服务端快照为准，避免本地乐观更新丢字段。

---

### 坑 2：「下一个」还能得 6 分，还吹 Canal/Lua

| | |
|--|--|
| **现象** | 候选人直接说「下一个 / 不会」，报告里仍有绿色 strengths，甚至写出题干里的技术点当优点 |
| **误判** | 「模型不够聪明」→ 想靠把 Prompt 写得更凶解决 |
| **根因** | ① 评分上下文把简历、题干、rubric、作答糊在一起，模型把「应该答的」当成「刚答的」；② 引擎盲目信任 LLM 的 `score/strengths`；③ 终评二次放大幻觉 |
| **修复** | Prompt **A/B/C/D 分区**；跳过/空答引擎硬封顶 1 分；`strengths` 与作答原文做重叠校验；终评 `_sanitize_report` |
| **原则** | **评分是安全边界，不是文案生成**；凡涉及分数与证据，控制面必须在引擎 |

**面试怎么说**  
> 我发现只靠 Prompt 防幻觉不够稳。所以做成两层：Prompt 分区降低诱发，引擎对空答封顶并对 strengths 做可核验过滤。这和内容安全一个思路——模型建议，系统裁决。

---

### 坑 3：知识库要不要微调 / few-shot / 向量？（设计坑）

| 方案 | 为什么当时不做 |
|------|----------------|
| 微调 DeepSeek | 接口侧基本不开放；成本高；题库还在变 |
| 超长 few-shot | 教的是格式不是万级知识；上下文装不下 |
| 一期就上向量 | 「语义相似」不等于「这轮该怎么挖」；可解释性差，难调试 |

**定案**

- 表一：八股题库；表二：项目拷打链（真实性核心）；表三：通用骨架  
- 公司 / 岗位是 **标签**，不拆笛卡尔表  
- 企业 / 岗位 **选填**（强制必填会丢掉无公司优质题）  
- 一期 **规则检索** 为主，向量留二期  

**面试怎么说**  
> 我刻意把「知识从哪来」和「话怎么说」拆开。知识在结构化题库与拷打链，模型负责组织语言。这样可测、可追责，也方便以后换模型。

### 坑 4：运维后台与额度

| | |
|--|--|
| **初版问题** | 统计嵌在用户壳子里；没有真正的用户/额度管理 |
| **根因** | 运维与 C 端信息架构耦合；额度不是可审计领域对象 |
| **修复** | 独立深色 `/admin`；`platform_quota` 默认 3；创建会话扣 1；自填 Key 不扣；`QuotaGrant` 流水；禁用用户 / 重置密码 / 清 Key |
| **原则** | 商业化能力要 **领域建模 + 审计**，不能只做 UI 展示 |

---

### 坑 5：KB 接通了，但「有量不准」

| | |
|--|--|
| **现象** | 召回一堆 Agent/RAG/多模态噪声；选「后端开发」几乎不起作用 |
| **根因** | `infer_roles("后端开发")` 靠技术关键词，缺别名映射 → `roles=[]` → **岗位过滤整段失效**；简历 `scene_tags` 脏标（如垃圾分类→AI）拽偏召回 |
| **修复** | `resolve_target_roles` 稳定映射；有目标岗时 roles **硬过滤**；弱化/关掉脏 scene 主导；项目链做主菜、全局检索做佐料 |
| **原则** | **错召回比空召回更伤**——产品会「看起来接了 RAG，其实更假」 |

---

### 坑 6：选了搜广推，整场却在问 Redis / 缓存击穿 ★（核心产品坑）

| | |
|--|--|
| **现象** | 目标岗位搜广推，面试官疯狂拷打简历里的 Java/Redis 项目原技术栈 |
| **误判** | 「题库没有推荐题」或「模型不听 target_role」 |
| **根因** | 规划 / 检索 / 拷打链实质是 **简历驱动**；`target_role` 只是 Prompt 旁白；岗位 ID 映射也不稳 |
| **技术 why** | 练习产品要考的是「适不适合目标岗」，不是「把简历再考一遍」。若不做硬约束，LLM 会走最熟的后端八股路径 |
| **修复** | ① 岗位解析落到 `recsys` 等 ID；② 有目标岗 → roles 硬过滤，skills/scene 弱加分；③ 拷打链按岗位视角改写（样本/特征/召回/排序）；④ Prompt 明确禁止「简历写啥考啥」 |
| **定案金句** | **目标岗位定方向，简历只提供素材。** |

**面试怎么说**  
> 这是我项目里最关键的产品决策。我把 target_role 从软提示升级成检索与规划的硬约束，并用搜广推案例回归。否则 RAG 接得越多，越像「简历复读机」。

### 坑 7：面试官说「简历提到了物联网」★

| | |
|--|--|
| **现象** | 简历是 Java/Agent，面试官却说简历写了 IoT/MQTT |
| **误判** | 「RAG 抽错题」或「解析简历失败」 |
| **根因（两层）** | ① 该场目标岗其实是嵌入式/物联网 → 问 RTOS **本身符合岗位优先**；② **归因幻觉**：把岗位考点伪装成简历经历 |
| **修复** | 简历可引用白名单；假归因句式改写成「结合目标岗位…」；Prompt 硬区分「候选人说过 / 简历真实出现 / 岗位考点」 |
| **原则** | Role-first 修好后，若不防归因，用户会以为「系统读错简历」——信任崩塌 |

**面试怎么说**  
> 我区分了「问得对不对」和「话术归因对不对」。岗位相关可以问，但不能谎称简历写过。我加了白名单和后处理改写。

### 坑 8：报告页看不到「★ 腾讯 原题」金色徽标 ★

| | |
|--|--|
| **现象** | 前端明明有徽标组件，报告永远不显示 |
| **误判** | CSS、条件渲染、没重启、旧缓存 |
| **根因** | 前端传展示名「腾讯」，题库存 id `tencent`；检索/标注用字符串全等 → 命中失败 → 无 `【企业原题】` → `original_company` 为空 → 徽标条件不成立。**是数据管道静默失败，不是 UI bug** |
| **修复** | `resolve_company_id` / `company_display_name` 边界归一；命中后回填 `plan.original_company`；终评 **原样透传、禁止发明** |
| **原则** | **词典 id ≠ 展示名**，必须在系统边界统一；涉及徽标/权限的字段要用集成测试钉死 |

**面试怎么说**  
> 我排查时先看了报告 JSON，发现字段一直是空的，才定位到 id/名称不一致。这类 bug 的特点是 UI「完全正确」但数据从未到达。

### 坑 9：八股都是 AI 编的，不像真题 ★

| | |
|--|--|
| **现象** | 报告里 Agent/RAG/MCP 题签很「像面试」，但 `from_bank=false`，没有库内题面 |
| **根因** | 规划官用 LLM 直接写 `ba_gu` 题签；「像真题」≠「是题库真题」 |
| **修复** | Planner **禁止输出 ba_gu**（输出也丢弃）；`pick_bagu_questions` 注入；提问用 `bank_question` 原文；参考答优先库内 `answer` |
| **原则** | 对用户承诺「真题/题库」时，来源必须是 **数据层强制**，不能靠模型自觉 |

---

### 坑 10：选了字节跳动，徽标却是「★ 其他海外 原题」★

| | |
|--|--|
| **现象** | 目标企业字节 + 岗位大数据；报告前两题标「其他海外」，第三题无标 |
| **误判** | 「公司词典配错了」或「前端写死了文案」 |
| **根因** | ① 库内几乎没有 `bytedance × big_data` 交叉题；② 通用 `retrieve` 把 company 当 **+120 加分（boost）不是硬过滤**，别家题（如 `coupang`→展示名「其他海外」）混进「字节召回结果」；③ 回退逻辑没先吃「字节任意岗位」的大池子（其实有大量字节题） |
| **修复** | `pick_bagu` 目标企业阶段 **硬过滤 `company==target`**；瀑布：企业×岗位 → 企业不限岗位 → 其他企业真题 → 无标签；徽标标**真实来源** |
| **设计澄清** | `retrieve`：企业 = boost（宽召回）<br>`pick_bagu`：企业 = hard filter（出题承诺） |
| **原则** | **宽召回用 boost，履约用 hard filter**；混用会「选了 A 却亮 B 的牌」 |

**面试怎么说**  
> 这是检索策略分层没划清导致的。我后来明确：给规划官的宽召回可以加分；真正决定「本场原题」的抽取必须硬过滤。并且交叉标签为空时，先回退到本企业题池，而不是直接跳到别家。

## 3. 从踩坑沉淀的工程原则（可写简历 / 口述）

1. **控制面在引擎，不在模型** — 分数、题源、追问上限、岗位硬过滤  
2. **目标岗位 > 简历技术栈** — 否则永远在复读简历  
3. **归因必须可核验** — 白名单 / 字面重叠 / 字段透传  
4. **id ≠ 展示名** — 边界归一，防静默失败  
5. **召回策略分层** — boost 扩池 vs hard filter 保承诺；瀑布应对稀疏交叉  
6. **错召回 > 空召回的伤害** — 脏标签会让 RAG「看起来很忙、结果很假」  
7. **服务端状态是真相** — 前端增量更新容易丢关键字段

## 4. 高频追问速答

### Q：为什么不用 LangChain / 多智能体框架？

> 角色已经拆开了（路由/规划/追问/评分/终评），但编排很浅，用一个状态机 + Prompt 切换就够。过早上框架会增加调试成本；我们把复杂度放在「题库与约束」而不是 Agent 拓扑。

### Q：和 ChatGPT 直接面试有什么区别？

> 三点：① 结构化题库与企业原题可追溯；② 引擎硬约束（空答、八股来源、岗位）；③ 会话状态、报告、额度、运维是完整产品，不是一次性聊天。

### Q：若题库某企业×岗位为空怎么办？

> 瀑布回退：先该企业其他岗位真题，再其他企业真题（徽标标真实来源），最后无标签八股。对用户诚实展示来源，而不是假装都是目标企业。

### Q：如何保证评分公平？

> 不保证绝对公平，但保证 **可解释与防崩**：分区 Prompt + 空答封顶 + strengths 证据校验 + 终评消毒。单测用 FakeLlm 锁住门禁行为。

### Q：最大的一次认知升级是什么？

> 从「把 Prompt 写得更强」升级到「**产品承诺必须落在控制面**」。搜广推、徽标、八股题源、字节/其他海外，全是同一课。

### Q：下一步你会做什么？

> 可选：向量检索作召回候选、交叉标签补全、拷打链质量评估、报告对旧会话的字段迁移工具。优先仍是「可测的约束」而不是堆模型。

## 5. 建议挂在简历上的项目描述（可改写）

**AI 模拟面试系统（独立项目）**  
- 设计并实现基于状态机的多角色面试引擎（规划 / 追问 / 评分 / 终评），LLM 仅生成语言，业务约束由引擎强制。  
- 构建万级结构化面经库与规则召回；支持目标岗位硬过滤与企业原题徽标；八股强制题库抽取，禁止模型编造。  
- 解决「简历驱动跑偏」「评分幻觉」「企业 id/展示名不一致」「boost/硬过滤混用」等关键问题，形成可答辩的迭代闭环。  
- 实现平台试用额度、自填 Key 不计费与独立运维后台（用户 / 额度 / 日志）。
