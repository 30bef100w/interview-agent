# 深问 MG / KG / TG 三图设计与标注流程

日期：2026-11-03。本文记录已经讨论确定的方向，并区分当前实现与后续设想。

执行顺序与P0/P1/P2交付见[MG/KG迭代计划](MG-KG迭代计划-2026-11-03.md)。

## 1. 一句话理解三张图

| 图 | 中文含义 | 回答什么问题 | 当前状态 |
| --- | --- | --- | --- |
| MG | 源题库与知识目录图 | 某个知识点下有哪些题，原题、答案和来源是什么？ | 已有3750题离线建图试验，继续整理数据 |
| KG | 项目/场景知识索引图 | 做过这个项目的人可能被问什么，项目涉及哪些知识点？ | 与MG共同建在离线图中，场景关联仍需整理 |
| TG | 面试追问轨迹图，亦称“拷打链图” | 针对这类岗位、知识点和作答情况，过去怎样逐层追问？ | **尚未实现，本文只记录设计思路** |

MG、KG是两种组织视图，物理上共享知识点和题目实体；TG未来再引用这些实体。三图不意味着把Redis复制三份，也不意味着必须建三个独立数据库。

本设计吸收QwenPaw-Data中分开组织元数据、知识关联和执行经验的思路，具体图结构按照面试任务设计，不声称与论文实现完全一致。

## 2. MG：从知识目录到源题

MG包含知识点的逐级组织、题目与知识点的挂载，以及原始内容和来源。

```text
后端基础（导航）
  └─ Redis
       └─ Redis缓存相关主题
            ├─ 缓存穿透 ←考察─ 题目A
            ├─ 缓存击穿 ←考察─ 题目B
            └─ 缓存雪崩 ←考察─ 题目C

题目A → 原始出现记录 → 来源文档
```

上图用于说明组织方式，不要求所有知识点都具有相同层数。通用缓存与Redis专有知识的范围要区别处理，不能把所有缓存知识都强制归为Redis专属。

### 知识点如何连接

- **细分关系**：父知识点→子知识点。允许一个节点有多个合理父节点，但层级不能成环。
- **主题覆盖关系**：某项技术或能力涉及一个主题；不适合表达为上下级时单独记录，不使用笼统的“相关”关系替代语义判断。
- **题目考察关系**：题目→实际考察的知识点。允许多知识点，也允许挂非叶子节点。
- **题目依赖关系**：题目→明确依赖的技术或前置知识，与主要考察内容分别记录。

例如“Redis分布式锁如何续期”，实际考点可以是锁续期机制；Redis是明确技术背景。若题目还要求比较Redis本身的特性，可以同时把Redis作为考点。不能因为答案提到Lua、网络、线程，就自动把这些全部当考点。

不要求每题逐级补齐所有祖先标签。若父级和细分知识点分别被实际考察，可以同时挂载。只连接一两题不是节点错误，不按题目数量裁剪知识点。

### 源数据与企业属性

原题、原答案、项目上下文和来源保留，答案为空就保留为空，不默认原答案正确。同一道题的多个来源可以汇聚到同一题目实体，但不丢失各来源内容。

企业、年份等作为题目或原始出现记录的属性；不创建企业节点。不同来源的企业信息分别保留，不从技术栈猜企业。时间戳不承担题目身份，相同短句也不意味着同一道题。

## 3. KG：项目就是场景入口

KG的主要用途是场景匹配：候选人有黑马点评项目，题库也有黑马点评相关面试经验，就可以找到更贴近该项目的问题。

```text
黑马点评（项目/场景入口）
  ├─涉及→ Redis ── MG中的同一个知识点
  ├─涉及→ 高并发 ── MG中的同一个知识点
  ├─涉及→ 秒杀 ── MG中的同一个知识点
  ├─直接相关题→ 题目A ── MG中的同一道题
  └─直接相关题→ 题目D

题目A ─考察→ 缓存穿透
题目D ─考察→ 防超卖
```

这是一份结构示意，不表示当前所有例子均已完成对应事实标注。

### 不强制增加中间层

不要求“业务场景→项目类型→项目模板→模块→主题”逐层拆分。“黑马点评”“点评类项目”等都可以作为并列入口，范围通过名称、定义和属性说明。

但二者不是同义词：普通点评项目不能直接判定为黑马点评。多个项目共享同一个知识点，通过知识点发生关联，不因此合并项目实体。

### 两种连接分别判断

1. **场景→题目**：题干点名该项目，或明确的项目章节/上下文能够证明归属。
2. **场景→知识点**：存在该项目涉及这个知识点的依据，逐项记录对应关系。

一道题提到多个项目、多个知识点时，AI应分别判断归属。不能把项目列表与知识点列表做笛卡尔积。仅因通用题涉及Redis和秒杀，不给它补“黑马点评”直接题关系。

题目可以没有场景。旧业务标签是待核查线索，不能冒充具体项目的已确认事实。

## 4. TG：汇聚真实面试中的追问链，尚未实现

TG希望积累所有用户产生的追问经验，按岗位或技术方向、关注点组织，再定位到具体会话中的链路。例如：

```text
Agent开发方向
  ├─ RAG侧重点
  │    └─ 链路A：某次会话中的RAG追问片段
  └─ 记忆侧重点
       └─ 链路B：另一次会话中的记忆追问片段
```

这是浏览和索引视图，不要求复制知识点，也不把某个用户建成知识树的必经父节点。一条链可以关联多个关注点，用相同链路ID复用。

### 记录什么

TG的基本单元是某次真实会话中的一条有上下文的追问链，而不是孤立的问题列表。建议保留：

| 数据 | 用途 |
| --- | --- |
| 链路身份、会话来源、岗位、项目/场景引用 | 定位这条经验适用的条件 |
| 各轮问题与实际作答，或其可追溯摘要 | 理解为什么出现下一问 |
| 下一问及触发原因 | 如回答含糊、暴露错误、声称做过某项优化 |
| 各轮知识点、题目引用 | 复用MG/KG实体；临时生成题可保留原文，不强行匹配已有题 |
| 原始顺序、分支及中断情况 | 保留真实轨迹，不凭空补齐“理想答案路线” |
| 已观察到的反馈及其来源 | 区分用户评价、模型判断与外部结果；没有反馈就明确为空 |

例如：

```text
问：RAG召回效果差，你怎么排查？
答：把top_k调大。
  └─追问：如果相关片段根本没入索引，调大top_k有用吗？
      答：……
        └─追问：你如何区分分块问题、召回问题和重排问题？
```

上例是未来数据结构示意，不是已经采集的链路。

### 怎样积累经验

先保存实际会话链，再把可复用的追问方式整理成候选经验。原始链路与提炼后的方法分别记录并互相引用。未来如使用skill-hub承载面试或简历方法，可以把提炼结果存为方法条目，并关联对应链路；当前尚未实现这一层。

链路越来越多代表经验覆盖扩大，不自动代表质量提高。频次、用户继续作答、模型自评都不能直接等价于“这条追问有效”。缺少外部反馈时，只能称为经验积累，不能声称已完成自进化闭环。

跨用户复用的是可共享的经验视图；原始个人简历和回答按会话权限保存，共享摘要应去掉个人身份信息。相似链路可以归入同一模式，但不能把不同用户的问答片段拼成一条声称真实发生过的链。

## 5. 三图怎样连通

统一知识点、场景、题目ID，是联通的基础：

```text
KG的项目 ─涉及→ 共享知识点 ←考察─ MG的题目
   │                                  ↑
   └─直接相关题───────────────────────┘

TG的真实追问轮次 ─引用→ 共享知识点 / 题目 / 场景
```

全图在数学上连通不等于需要全部取出。后续检索使用允许路径和深度、广度预算，题目去重并保留命中依据；本轮先完成离线图，不实施检索或新增向量/BM25通道。

## 6. 固定生产流程：AI判断，脚本建图

```text
原题 + 必要上下文 + 当前索引
  → AI逐题判断并批量输出明确标签/关系
  → AI核查新增节点、同义项与父节点，形成索引变更
  → 脚本检查格式、引用、重复与层级环
  → 按明确标注构建MG/KG
  → 中文目录、真实子图、变更清单
```

AI先查看相关索引分支、定义和全局别名；复用已有概念，缺失才新增。脚本负责确定性校验和落图，不通过关键词、英文编号前缀或标签交叉组合代替语义判断。

现有标签保留为复核底稿，不全量推倒。非题目记录排除，依赖上下文的题尝试补全，仍不明确的保留待处理。`TESTS`与`REQUIRES`分开记录；新增节点先作为提案，完成语义核查后进入正式注册表，不要求每条提案人工审批。

详细规则见 [离线建图与题目标注规范](MG-KG离线建图与题目标注规范-v1-2026-11-03.md)。可复用skill源码位于 `skills/annotate-interview-questions/`。

## 7. 当前实现边界与后续工作

当前快照：3750题、2209个知识点（含33个导航节点）、48个场景。3750题完成挂载结构检查，334题完成原题二次语义复核。159条被单列处理，原因包括缺上下文、碎片和非题目，不全是不可恢复的题。

目前建图与审核脚本仍有按前缀补父级、场景共现连边、默认草稿状态等历史行为；新规范和标注skill不代表这些代码已经修复。skill的新输出协议也不能不经适配就直接交给旧脚本。图检索尚未接入生产，TG尚未建立。

后续先修正上述脚本行为、整理现有标注并重建离线图，再分别推进检索和TG。参赛材料应按此区分“已实现”“离线试验”和“规划”。
