# 深问运营指标：实习项目对照与改造方案

日期：2026-11-09。依据本地源码静态检查；本文区分已有实现、发现的问题和建议方案。本文不代表功能已经上线。

后续改造已完成第一版，实施范围与验证见[运营分析指标实现](./运营分析指标实现-2026-11-09.md)。下文保留改造前的审查结论。

## 1. 结论

当前深问概览偏向数据盘点：累计用户、累计面试、累计支出和最近会话。实习项目最值得借鉴的是把指标定义、时间比较、趋势、维度拆分和明细串起来，使运营能回答“哪里变化、变化来自哪里、该查哪条记录”。

不宜直接复制实习项目的业务指标或引入整套 BI 平台。其大量指标值、同比环比及达成率由上游数据源提供，这个代码包没有完整的数据仓库计算实现。可以借鉴查询与展示结构，在深问自己的数据层实现适用的口径。

## 3. 深问当前存在的口径问题

### 3.1 活跃用户不能代表实际答题用户

[AdminRepository.stats()](/Users/xuyongqi/Desktop/fa/interview-agent/backend/app/repositories/admin.py:36) 只用 `User.last_active_at` 计算 DAU 和近 30 天活跃数，没有排除管理员。

这个时间在注册、登录、飞书登录和面试创建成功时更新；正常回答问题不会更新它。管理员本地预览登录也会进入当前活跃数。最后一次活动时间还会被覆盖，不能靠这个字段恢复过去每天的 DAU。

近期可直接从 `Answer.created_at → InterviewSession.user_id` 得到“每日已答题用户”，并按用户去重。这一明确口径也能计算历史答题留存，前提是历史记录保留完整。更广义的使用活跃（复习、读报告等）需要补业务事件。

### 3.2 面试完成不等于报告生成成功

[_close_with_report()](/Users/xuyongqi/Desktop/fa/interview-agent/backend/app/api/interview.py:846) 在终评异常后写入兜底报告，仍将会话标为 `finished`。

因此“finished 场数”“有 ScoreReport 记录的场数”和“获得正常终评报告的场数”含义不同。不能用报告表有记录就声称生成成功。建议新增结构化报告状态 `success / fallback / failed`，并保留生成尝试时间和错误类别。历史数据只能作明确标注的近似识别，无法识别的归为 unknown。

### 3.3 JSON 解析失败会重复增加模型调用计数

[OpenAiLlm.chat_json()](/Users/xuyongqi/Desktop/fa/interview-agent/backend/app/services/llm/client.py:98) 在解析之前记录一次调用成功；如果随后 `_parse_json()` 抛异常，except 又记录一次失败。同一次尝试因此会被计数两次。

应当把“供应商请求成功”和“结果解析成功”分别记录，每次物理调用只产生一条尝试记录；逻辑请求是否最终成功另算。否则调用次数、失败率和耗时分布会失真。

### 3.4 运行指标与经营周期不一致

[MetricsRegistry](/Users/xuyongqi/Desktop/fa/interview-agent/backend/app/observability/metrics.py:8) 在进程内聚合，重启清空；次数覆盖进程存活期间，耗时仅保留各桶最后 500 个样本。这些数不能直接用于“本周调用量”和“本周 P95”。多进程部署还会各自持有不同结果。

深问已有 [session JSONL 节点追踪](/Users/xuyongqi/Desktop/fa/interview-agent/backend/app/observability/node_trace.py:45)，可辅助排障；但它不是覆盖全部模型调用、统一时区和时间范围的持久化指标表。可以保留即时监控，再补周期统计所需的事实记录。

### 3.5 成本是估算用量，调用记录也有覆盖边界

[LLMUsage](/Users/xuyongqi/Desktop/fa/interview-agent/backend/app/models/llm_usage.py:25) 有模型、tokens、估算成本和时间，没有成功状态、耗时、业务节点和重试关联；供应商未返回 usage 时，[client.py](/Users/xuyongqi/Desktop/fa/interview-agent/backend/app/services/llm/client.py:75) 不写用量。该表行数不能直接叫作全部调用次数，估算成本也不应直接叫账单实付。

## 4. 深问第一批应做的指标

默认北京时间，区间采用开始包含、结束不包含；业务分析排除管理员和明确标记的测试账号。禁用账号的历史行为应保留，避免禁用操作改写过去的统计。

| 指标 | 建议计算口径 | 现有数据支持情况 |
| --- | --- | --- |
| 新增用户 | 区间内创建的业务用户数 | 可算 |
| 已答题用户 | 区间内至少有一条持久化 Answer 的去重用户数 | 可算；称“已答题”，不把文本存在等同于回答质量达标 |
| 已答题面试 | 区间内至少有一条 Answer 的去重会话数 | 可算；与仅创建会话分开 |
| 首次答题转化率 | 同一注册用户群，在注册后固定 7 天内首次答题的人数 / 该群总人数 | 可从现有时间戳计算；仅比较已经完整观察 7 天的用户群，未成熟群单独标记 |
| 面试完成率 | 按创建时间选同一群会话，在创建后固定观察窗口内完成的场数 / 该群创建场数 | 可算窗口内完成；窗口长度需统一配置，未成熟会话不与成熟群混算 |
| 退出与滞留 | 明确 abandoned 场数；长期未继续的 active 会话另列“疑似流失” | 明确退出可算；未操作不应直接标作退出，需补最后业务活动时间 |
| 正常报告交付率 | 同一会话群在观察窗口内获得正常报告的场数 / 该群已完成场数 | 需先区分正常报告、兜底报告和未知历史结果 |
| 答题 D1 / D7 留存 | 首次答题日为 D 的用户中，在 D+1 / D+7 自然日再次答题的去重人数 / D 日首次答题人数 | 可基于历史 Answer 计算；观察日未到时不展示 0 |
| 单场平台估算成本 | 创建于选定区间的会话，截至同一观察时点已记录的平台成本 / 该群会话数 | 可算；包含完成、失败、退出和未完成场次，附用量覆盖限制；无 session_id 的成本单列 |
| 模型调用失败率与 P95 | 同一区间内失败物理尝试数 / 全部物理尝试数；在同一批尝试耗时上计算分位数 | 需持久化尝试结果、时间与耗时，并先消除重复计数 |

“期间平台支出”另外按 `LLMUsage.created_at` 汇总，用于看当期消耗。它和按会话创建群归集的单场成本是两种视角，不应混用分子分母。

## 5. 从指标走到问题定位

第一版首页建议只保留 6 个主卡：新增用户、已答题用户、已答题面试、面试完成率、正常报告交付率、单场平台估算成本。每张卡包含本期值、上期值、变化、趋势、口径说明和可点击的明细入口。累计规模可放在辅助位置。

下方安排三组分析：

1. 用户路径：同一注册群的注册 → 有简历记录 → 创建面试 → 首次答题 → 完成 → 正常报告，能看到每步流失。简历表目前只有创建时间，没有独立解析完成时间，因此第一版只能称“有简历记录”，不能声称“解析成功”。
2. 面试类型拆分：按面试模式、类型查看创建量、已答题场数、完成率、退出率及样本量；再进入该组会话明细。
3. 成本与质量：按 provider / model 查看用量和成本；补节点及重试事实后，再分析规划、追问、评分、终评各阶段的耗时、失败和重试支出。

对可加总指标，可展示各维度绝对变化 `本期组值 - 上期组值`，用于定位总变化来自哪些组；比例指标应从各组分子分母重新汇总，不能平均各组完成率。增速榜与增量贡献榜分开。总变化为 0 或接近 0 时，不展示不稳定的贡献百分比。

例如“本周完成率下降，主要集中于全流程面试；相关会话多数在首答后未继续”属于可核查的定位结论。仅有这一关联还不能断言“用户不喜欢全流程”，应连接明细、错误和反馈进一步验证。

## 6. 实施顺序与验证重点

1. 先修正指标基础：明确业务用户范围，纠正 JSON 尝试重复计数，区分报告成功与兜底。
2. 用现有持久化数据实现已答题用户、趋势、成熟用户群转化与留存、类型拆分、会话成本；统一时间筛选并支持明细核对。
3. 补持久化业务事件和模型调用尝试，再做跨重启的错误率、P95、重试成本、节点分析及异常提示。

无需为了第一版引入数据仓库。沿用现有 Repository / Service / API 分层即可，后续数据量增长再决定是否增加日汇总表。

应重点验证：零值与空值、分母为零、跨北京时间零点、未成熟观察窗口、管理员排除、每次物理调用只计一次、兜底报告不算成功、会话与用量表关联后不重复累计成本。
