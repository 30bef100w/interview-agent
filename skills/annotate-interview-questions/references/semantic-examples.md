# 影响标注决策的判例

以下以中文概念说明判断；实际输出必须查当前注册表的ID，不照抄示例创造同义节点。

## 语义复核顺序

按“领域 → 对象 → 所问机制 → 对应节点”判断，再对照旧标签决定保留、删除或新增。领域不明确时查准确来源和必要的原答案，不以节点名称里出现一个相同单词就认定匹配。短理由写明所问对象/机制，不用“某某题”“按场景库复核”代替关系判断；无需逐题写长分析。

逐项保留能够成立的考点，不设机械标签配额：问题要求比较多个机制或设计完整链路，可以有多个标签；只是解题时可能选用某技术，不等于考察该技术本身。新增一个更细标签也不能掩盖旧的错误标签，输出前检查是否应删除旧标签。

父子节点要做一次共现判断：题目问“Redis 数据结构，以及 Hash 扩容”时可以同时保留`redis.data_structures`和其细节点；题目只问“Hash 扩容”时通常保留细节点，不因索引层级自动补上父节点。校验器报告共现只是审计提示，不能代替对题干的判断。

复用节点前核对定义及父路径；缺少定义时结合中文名、上级范围与真实题意判断。如果现有节点本身归错领域，输出索引修正依据，当前题使用语义正确的节点或提出必要新概念，不为了“复用已有节点”继续错挂。不能用删掉全部细标签的办法躲避判断。

## 实际错标的边界

| 问题 | 应避免的判断 | 正确判断方向 |
| --- | --- | --- |
| C++面经中的string字节序 | 看到string就挂Java字符串 | 根据语言上下文判断C++与字节序；不照抄不可靠的原答案结论 |
| 视频生成中的Reference Bank、Memory Token、State Propagation | 看到memory/state就挂Agent记忆、Checkpoint | 原章节与原答案指向长视频跨片段一致性；既有Reference Bank节点归Agent也需提出纠正 |
| 用大模型设计音乐推荐系统 | 大模型+数据就挂Data Agent/ChatBI | 推荐系统与模型应用；推荐和问数不是同一任务 |
| Cline的Plan/Act模式 | 名称近似就等同自主Plan-and-Execute执行范式 | 先辨别交互模式、工具权限和执行机制；只有原题确实比较执行范式时才加该考点 |
| GraphQL编辑器query自动补全 | 自动补全就挂AI交互 | 类型schema、语言服务或编辑器补全；没有AI证据不挂AI长任务等节点 |
| 如何设计Prometheus metric | 可观测性都归日志/Trace | 指标设计与采集；metrics、logs、traces有关联但不是同义考点 |
| 项目里的索引分几类 | 同时猜MySQL索引和向量索引 | 先确定项目与索引对象；无法恢复则待上下文，不把所有可能类型都挂上 |
| 如何接收后端消息 | 默认就是SSE | 先明确消息接收/通信机制；未指定时不能把一种候选协议标成实际考点 |
| 买票超时自动取消 | 默认Redis过期就是实现 | 考察延迟任务/订单时效机制；Redis只在题干或有效上下文明确要求时单独标注 |
| 递归空间复杂度 | 递归就加动态规划 | 递归深度、调用栈和复杂度；不是所有递归都涉及DP |

## 上下文与项目归属检查

省略题先看源记录已有答案和准确章节，必要时定向读取原文；读过的依据写入`context_refs`，能可靠还原才补`normalized_question`。“Redis编码转换为何不可逆”之类可恢复内容不能仅因题干短就长期搁置。确实缺少必要指代时保留needs_context；手册标题、工具维护规范、页面字段等另判断是否根本不是面试题，不统一塞入待上下文。

采用足够判断主题的证据标准：`HTTP`、`数据库`、`Kryo`即使只有标题也能保留为概述材料；不必为了细粒度索引猜子节点。`304`在HTTP资源缓存上下文中可定位状态码；LRU准确章节里的“数据结构设计”“易错点”可恢复为LRU主题。题目问“怎么接收后端消息”，只确定消息接收即可挂该宽考点，不必在SSE与WebSocket间猜一个。没有答案不妨碍语义标注，缺代码也不妨碍确定“工作流代码节点”这一主题；但要求实际审查一段未提供的代码、或原创算法题题面完全遗失，仍需保留待补。恢复题意和生成正确答案是两回事。

“有城市的倾向吗”“项目的衡量标准是什么”“复杂翻译项目如何规划”都是可直接提问的完整开放问题，可以无技术标签，不必知道候选人的真实城市、项目或翻译内容。只有“问项目”“一道树题，做了十分钟”则缺实际题意，不能换成自行编写的项目题或树算法题。工作区的写作规范、报告样本准入和维护流程属于非题目，不能为减少待补数而强挂技术标签。

场景检查关注“谁使用、系统担任什么角色、完成什么任务”。AI面试官向候选人提问；候选人答题助手向候选人提供回答建议，不能按“面试”二字归为同一场景。原答案直接说明本题系统身份时可用来澄清，不把其中泛举的其他业务当项目归属。

除了题干点名，也检查准确项目章节。例如`电商问数/16-查询接口实现与依赖组装.md`中的“main.py作用”有明确项目线索；通用题干不代表必定无场景。反过来，只有大合集目录或共享技术，不足以证明具体项目身份。加入场景后，知识点关系仍独立判断：仅“介绍分布式文件存储项目”不能自动证明项目使用某种一致性算法。

## 已知问题回归与交付范围

先逐项检查上一轮明确指出的问题，再抽看新增范围；回归样例见[固定错标案例](semantic-regression-cases.json)。脚本检查该固定题库中已确认的禁用关系与必需关系，不替代AI判断新题，也不能据此报告全库准确率。已知错误未改、场景仅提案未正式入库、必要上下文尚未查阅时，应分别如实报告。

“导出数据太大内存放不下怎么办”“AXI-FULL协议怎么用”是明确技术题。索引找不到合适节点时，按已有/新增节点流程处理；不能以“避免硬套”为理由交付空考点且没有提案。“Spring控制反转、AOP”明确列出两项，需分别核对考点是否覆盖；只保留Spring泛节点不能掩盖漏掉AOP。朋友圈信息流系统设计不因也叫“系统设计”就挂到Agent系统设计。

新复核记录用`review_scope`区分full、concept_only、scene_only、status_only。只有full才计入完整复核；旧数据缺少此字段时不倒填完成标记。输出文件行数和review字段本身均不能证明模型确实读过题。

## 实际考察与依赖

“Redis分布式锁如何续期？”：考察锁续期机制，Redis是明确技术背景。先查现有分布式锁分支和别名，找到对应机制再挂载。若已有节点正好是Redis分布式锁，可直接复用；不要求为了标签精细而新建一条仅改措辞的节点。是否另挂Redis考点取决于题目是否实际考察Redis原理，不机械重复。

“为什么Lua脚本能保证这一段操作的原子性？”：如果实际要求解释原子性，Lua/Redis执行机制可成为考点，不因上一例将Lua视为背景就统一降为依赖。

原答案中的常见解法不自动成为考点。题目问缓存穿透，答案提到布隆过滤器，只能说明它是一个候选解法；没有进一步要求时，不把所有解法实现细节全挂为独立考点。

## 场景归属不能靠技术组合猜

“秒杀时如何避免超卖？”：可以挂秒杀、防超卖，场景可空。

“你在黑马点评中怎样避免优惠券超卖？”：按本地生活业务归类，连接本地生活服务→题目，教程名留在原文和来源属性中；按原文明确关联场景与考点。简历写本地商户优惠券业务也可匹配此场景，不必出现黑马点评名称。

题目同时比较“黑马点评的Redis库存方案”和“另一个RPC项目的负载均衡”，分别确认本地生活场景及另一项目的业务归属，只建立各自有依据的场景→知识点边，不生成四种交叉组合。

答案拿电商、客服作类比，不代表题目来自这些项目。文档是大合集时，目录里有黑马点评章节也不表示整份文档的题都属于黑马点评。

## 已有节点与新节点

“Cache Penetration”和“缓存穿透”是同义表示，复用同一ID。“缓存穿透”和“缓存击穿”不是同义，不因都只挂一两题就合并。

某知识点已在数据库分支出现，又适合分布式分支：复用实体，判断是否需要另一条父关系；不要另建一个分布式版同义节点。

编号前缀很像某一技术并不证明从属关系。父节点需符合实际知识范围，不能只为消除孤立节点而接入任意上级。

## 不完整题与噪声

真实S0128：“三兄弟里，哪一个最容易被面试官继续追问细节？”原答案及来源指向缓存穿透、击穿、雪崩。先核对原文范围，能够还原时保留原题，并在normalized_question补全对象、写context_refs。

“它的瓶颈在哪？”缺少指代对象：若原文不可用，标needs_context，不标成通用性能瓶颈就算完成。

“￥25”“合计”“首页-未点餐”：通常是采集混入的页面文字，结合记录确认后标not_question，不建立价格知识点或外卖项目面试题。

“你如何处理团队意见不一致？”可作为行为面试题保留，技术考点可空。不能因它没有技术节点就当垃圾排除。
